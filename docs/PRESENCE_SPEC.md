# VERSE CITY 相互プレゼンス連携 仕様 v0.3

ブラウザ版メタバース（VERSE CITY Web）と VRChat版 VERSE CITY の間で、
「どちらの世界にいる人も、もう一方の世界の客席にアバターとして現れる」ための連携仕様。

- 作成: 2026-07-14 ／ v0.2: 未決事項への回答反映 ／ **v0.3 (2026-07-15): Unity側返答（HANDOFF_REPLY_FROM_UNITY.md）の統合方針を反映・両チャット合意**
- ステータス: **合意済み・presence.json は v=1 で凍結**（変更は両チャット協議＋バージョン上げ）

## v0.3 での重要な構成変更（Unity側 ALLVERSE 基盤との統合）

- **VRCワールドは presence.json を直接読まない。** Unity側の ALLVERSE Worker（Cloudflare）がサーバー間で
  presence.json を取得（4秒キャッシュ）し、ワールドへは Worker の live.json 1本で配信する。
  → ブラウザ側サーバーの改修はゼロ。presence.json は公開GETのまま
- ts鮮度判定・Renderスリープ復帰の吸収は Worker 側が担当
- §2.4 の「マスター取得＋同期変数」推奨は撤回（Unity側の裁量で全クライアント取得方式を採用）
- **`yt[]` は実装しない（常に空・スキーマ互換のため残置）。** YouTube系データはALLVERSE Workerが正
- 中間ソフト（§3.2）は ALLVERSE の harvester に一本化（`[VCITY1]` 行は本サーバーへ、`[ALLVERSE]` 行はWorkerへ送り分け）

## 2. 方向①: ブラウザ & YouTube → VRC

### 2.1 エンドポイント

```
GET /api/presence.json
```

- 認証: なし（公開・読み取り専用。個人情報は表示名のみ）
- 更新: サーバー内部では常時最新。VRC側の取得間隔は約5秒
- サイズ上限目安: 30KB以下（VRCの文字列ダウンロードに余裕を持たせる）

### 2.2 レスポンス形式

```json
{
  "v": 1,
  "ts": 1789400000,
  "web": [
    { "rm": 1, "n": "loy", "x": 3.2, "z": -12.5, "r": 90,
      "av": { "h": "twin", "hc": 5, "sc": 0, "bc": 1 },
      "c": ["今日のライブ楽しみ！", 1789399995] }
  ],
  "yt": [
    { "n": "コメントした人の表示名", "t": 1789399990 }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `v` | 仕様バージョン（互換性判定用） |
| `ts` | サーバー時刻（UNIX秒）。VRC側の鮮度判定用 |
| `web[]` | ブラウザ勢。**インスタンス番号昇順（#1→#2→…）で整列済み**。`rm`=インスタンス番号, `n`=表示名, `x`/`z`=ワールド座標(m, 小数1桁), `r`=向き(度, 整数), `av`=アバター見た目 |
| `av` | `h`=髪型id, `hc`/`sc`/`bc`=髪色/服色/肌色のプリセット番号（対応表は付録A）。VRC側プロキシアバターに同じカスタムを再現するために使う |
| `c` | 【任意・機能フラグで有効化】直近発言 `[本文, 時刻]`。直近30秒以内の発言がある人にだけ付く。使うかは運用してから判断 |
| `yt[]` | YouTubeチャット発言者。`t`=最終発言時刻 |

- **複数インスタンス時の表示ルール（確定）**: VRC側ギミックが表示上限（VRC側で決める）まで `web[]` を先頭から順に採用する。配列は#1から順に並んでいるので、結果的に「#1から順にインスタンスまたぎで上限まで表示」になる。サーバー側は並び順を保証するだけで、上限判断はVRC側に持たせる
- 座標を送るのは `web[]` のみ。`yt[]` は「出現させる人のリスト」だけ（配置はVRC側ギミック任せ＝現行仕様踏襲）
- 30KB制約のため `web[]` は最大60人、`yt[]` は直近発言者最大100人でトリム（`c` を有効化した場合も上限内に収まるよう本文は最大40文字でカット）

### 2.3 座標系の取り決め

> **2026-07-30 変更**: 下記の「ステージ中心原点」から **VRChatワールド座標そのまま** に変更した。
> 理由: ブラウザ側の会場がVRChatのVERSE CITY2025から書き出した同じメッシュになり、
> 変換で戻せるようになったため。**VRC側の吸収処理は不要**（loyさん判断: VRC側は直すのが大変）。

> **2026-07-30 追記（イベント運用の変更）**: 常設イベントを廃止した。
> `web[]` に人が出るのは「①管理人がイベントを立てている ②そのイベントの
> 『VRChatに出す』設定がON ③人が入っている」の3つが揃ったときだけ。
> VRC会場は1つなので、連携ONにできるイベントも1つだけ。詳細は `HANDOFF_UNITY_4.md`。

**現行（v0.4 相当）**

- `x`/`z` は **VRChatワールド座標をそのまま**送る。VRC側は受け取った値をそのまま置いてよい
- `r` も **VRChatのY回転（度・0〜359）**。そのまま使ってよい
- 単位: メートル。Y（高さ）は送らない（両世界とも床基準で配置）
- ブラウザ側の会場（clubVERSE）が占めるVRC座標のおおよその範囲:
  - X: −234 〜 −196 ／ Z: −88.4 〜 −66.9（歩ける範囲。38m × 21.5m）
  - 会場中心 = VRC(−209.0, −71.91) ／ 会場入口 = VRC(−213.9, −61.6)

変換はブラウザ側サーバー（`server/server.js` の `toVrcX` / `toVrcZ` / `toVrcRot`）で行う。
根拠と検証記録はその関数のコメントにある。X軸と回転の符号が反転するのは、
Unity(左手系)から書き出して three.js(右手系) へ取り込んだため。

**旧（v0.3まで・参考）**

- 原点: メインステージ中心の床面
- +X: ステージに向かって右 ／ -Z: ステージ正面方向（客席からステージへ向かう向き）
- VRC側ワールドとズレがある場合は、VRC側ギミック内の定数（オフセット＋回転）で吸収する

### 2.4 VRC側（Udon）実装ガイド

- `VRCStringDownloader.LoadUrl` で5秒間隔取得 → `VRCJson` でパース
- **インスタンスマスターのみが取得**し、同期変数で全クライアントに配布（負荷と不整合の回避）
- 座標反映は即時ワープではなく、次回更新までの約5秒かけて歩行補間
- `ts` が60秒以上古い場合は「サーバー停止中」とみなし、ブラウザ勢の表示を退場処理

## 3. 方向②: VRC → ブラウザ（実装可能な設計だけ先に確保）

### 3.1 Udonログ出力仕様

- ワールド内のUdonが 1秒間隔で全プレイヤー位置をログ出力
- 出力ON/OFFはワールド内のスタッフ用スイッチ（既定OFF。オーナー/スタッフだけONにする）

```
[VCITY1]{"p":[["VRCユーザー名",3.2,-12.5,90],...]}
```

- 行頭マーカー `[VCITY1]`（末尾数字=バージョン）。中間ソフトはこのマーカー行だけを拾う
- 座標は小数1桁、向きは整数（ログ肥大防止）

### 3.2 中間ソフト（コンパニオンアプリ）

- 対象: `%USERPROFILE%\AppData\LocalLow\VRChat\VRChat\output_log_*.txt` を末尾監視
- マーカー行をパースし、1秒ごとにまとめてサーバーへ送信:

```
POST /api/vrc-presence
Authorization: Bearer <スタッフ用トークン>
{ "src": "起動者の識別子", "ts": ..., "p": [["VRCユーザー名", x, z, r], ...] }
```

- 複数人が同時起動していた場合、サーバーは最新 `ts` のソースを採用（自動フェイルオーバー）
- トークンはポータルのスタッフ権限で発行（誰でもPOSTできる状態にはしない）

### 3.3 表示フィルタ（承認の実装）

- サーバーは受信した VRCユーザー名を**ポータルの「VRC連携登録」テーブルと照合し、登録済みの人だけ**ブラウザへ配信する
- 未登録者はサーバー側で破棄（ブラウザには一切送らない）
- ブラウザ側表示: 登録時に選んだプリセットアバター or 汎用シルエット＋VRCユーザー名

## 6. YouTubeチャット取得の一本化について（検討メモ）

現状は「YouTubeのチャット欄から発言者を取ってくる仕組み」が2か所に生まれうる:

- (a) 既存: VRC側ギミックが自前で取得している経路
- (b) 新規: ブラウザ版サーバーが、ワールド内にYouTubeチャットを表示するために取得する経路

**案A: サーバーに一本化** — (b)だけ動かし、VRC側ギミックは presence.json の `yt[]` を読む形に切り替える。
利点: YouTube APIの消費が1系統で済む／発言者リストが両世界で完全に一致／取得ロジックの保守が1か所。
欠点: 既存ギミックの取得部分を作り替える必要／サーバーが止まるとVRC側のコメント勢出現も止まる。

**案B: 並存** — 既存ギミックはそのまま、サーバーは別途取得。
利点: 動いているものを触らない。 欠点: 二重取得でAPI枠を余計に消費、リスト不一致の可能性。

推奨は**案A（一本化）**。ただし移行時期は「サーバー本実装が安定してから」でよく、それまでは案Bで並走可能。
