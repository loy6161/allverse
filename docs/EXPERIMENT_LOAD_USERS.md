# 実験: 実ユーザーは何人まで入れるか（2026-08-06）

loyさん「ユーザーが何人くらいは入れるかをテストしたいんだから。」

測り方: `server/loadtest_users.js`。仮想クライアントを大量につないで、
本物と同じ **10Hz で位置を送る**。別に「観測役」を1人立てて、
自分の発言が返ってくるまでの**往復時間**を測り、伸び始める点を限界とみなす。

```bash
cd server && node loadtest_users.js 10,30,60          # 全員1ルーム
ROOMS=32 node loadtest_users.js 480                    # 32ルームに分ける
```

---

## いちばん大事な結論

**効くのは「総人数」ではなく「1ルームの人数」。**

位置は同室の全員へ配られるので、通数は **人数の2乗**で増える
（N人 → 1秒あたり N × 10 × (N−1) 通）。ルームを分ければ、総人数が増えても通数は増えない。

| 総人数 | 1ルームの人数 | 通数/秒 | 往復（中央値 / 95%） | 判定 |
|---|---|---|---|---|
| 10 | 10 | 920 | 1ms / 2ms | ◎ |
| 30 | 30 | 8,749 | 1ms / 2ms | ◎ |
| 60 | 60 | 35,266 | 1ms / 8ms | ◎ |
| 120 | 15 | 70,488 | 1ms / 11ms | ◎ |
| **240** | **15** | 33,459 | 1ms / 7ms | ◎ |
| **480** | **15** | 66,914 | 1ms / 8ms | ◎ |
| **960** | **15** | 134,228 | **575ms / 623ms** | ✕ 詰まった |
| 240 | 30（8ルーム） | 141,576 | **394ms / 608ms** | ✕ 詰まった |

**壁は「約10万通/秒」**。人数の並べ方に関係なく、ここを超えると往復が数百msに跳ねる。

- 全員1ルーム … **100人**で 99,000通/秒 ＝ ちょうど壁
- 15人ずつのルーム … **600〜700人**まで
- 30人ずつのルーム … **300人**くらいまで

⚠ **この数字はこちらのPCをサーバーにして測ったもの。**
本番の Render は無料枠（CPUを他と分け合う）なので、**これより確実に低い**。
本番の実数を知るには本番へ向けて測る必要がある（それ自体が本番の負荷になるので要許可）。

---

## もう一つの壁: 見る側（ブラウザ）

サーバーが耐えても、**画面に他人が何人映るか**で先に苦しくなる。
他人1人＝アバター1体＝**約12回の描画**・517三角形。

| 画面に映る他人 | 1フレーム（GPUあり） | loyさんの環境の推定（×15） |
|---|---|---|
| 0人 | 3.5ms | 52ms |
| 10人 | 2.3ms | 34ms |
| 30人 | 4.5ms | 68ms |
| 60人 | 6.4ms | 96ms |

loyさんの環境（GPUを使わない設定）だと、**60人が同じ部屋に居ると 1フレーム 90ms 台＝11fps**。
**実用は1ルーム20〜30人**が目安。いまの定員上限（60人）は、サーバーではなく
**見る側の都合で決まっている**。

---

## つまり

- **同時接続そのものは数百人いける**（1ルームを小さく保てば）
- **1ルームは20〜30人**にしておくのが現実的（見る側の負担で決まる）
- 人数を増やしたいときは**定員を上げるのではなく、ルームを増やす**
- 本番（Render無料枠）の実数は未測定。測るなら許可がほしい

## 管理者用の測定ボタン（2026-08-06追加）

loyさん「管理者用にNPCとは別に、測定できるものを付けておいて。10000人くらいまではかってみたい。」

**⚙設定 → 管理 → 「負荷の測定（何人まで耐えられるか）」**（管理者のみ）。

- 人数（最大20000）と1ルームの人数を入れて「測定を始める」
- サーバーの中に**仮想ユーザー**を作り、本物とまったく同じ配信処理を回す
- **実ユーザーには1通も届かない**。ただしサーバーのCPUは本当に使う
- **3分で自動停止**（測りっぱなし防止）

出る数字:

```
△ そろそろ限界
仮想ユーザー 1000人（15人 × 67ルーム）
遅れ 平均0.5ms／最大2ms
配信 139,500通/秒（7.6MB/秒）／実接続の限界は約130,000通/秒
処理に使った時間 36ms/秒（1000で限界）
メモリ 107MB／経過 3秒
```

### アバターを出して目で確かめる（2026-08-06追加）

loyさん「これは数値だけ？実際にあばたーはでないの？だして検証したい。」

「見せる」欄に人数（**最大5000**）を入れると、その人数ぶんが**実在の人とまったく同じ仕組み**
（remote.js）でアバターとして出る。名前も付き、動きもする。

- 出るのは**測定した本人の画面だけ**。お客さんには1体も出ない
- 位置は1周期に1通へまとめて送る（1人ずつ送ると回線が先に詰まるため）
- 測定を止めると自動で消える
- 上限は 5000人（2026-08-06に300から引き上げ）。
  loyさん「上限300は少ない ぜんぜん動くよ。5000にして。負荷テストなのに
  セーフティーにしてどうするの？テストにならん」。
  **こちらの見積もりで頭を押さえない**。動かなくなる点は実際に出して見つける

これで「サーバーが捌けるか（数字）」と「自分の画面が耐えられるか（見た目とfps）」を
同時に確かめられる。fps表示（⚙設定→表示設定）と一緒に見ること。

⚠ **この測定に含まれないもの**: 通信の書き出し（ソケットへの write）。
組み立てまでの費用しか測れないので、**実接続で測った限界 13万通/秒**と見比べること。
上の例は 139,500通/秒 なので、**1,000人（15人ずつ）で既に実接続の限界を超えている**。

### 1ルームの人数に上限は付けていない

loyさん「1ルームの上限決めないで。それもテストしたいから」。1ルーム1万人なども試せる。

⚠ そのまま回すとサーバーが固まる（1ルーム1万人＝1周期あたり約1億通で、
その間サーバーは何も応答できない）。そこで**1周期60msで打ち切り、
「捌けなかった通数」を結果として出す**。捌けなかった量そのものが「この設定は無理」の答え。

実測（こちらのPC・仮想ユーザー）:

| 人数 | 1ルーム | 本来必要 | 実際に捌けた | 捌けなかった | CPU |
|---|---|---|---|---|---|
| 1,000 | 15 | 139,500通/秒 | 139,500 | 0 | 36ms/秒 |
| 10,000 | 15 | 1,399,500通/秒 | 1,373,890 | 25,610 | 596ms/秒 |
| **300** | **300（全員1部屋）** | 897,000通/秒 | 897,000 | **0** | 370ms/秒 |
| **1,000** | **1,000（全員1部屋）** | 9,990,000通/秒 | 1,490,944 | **8,499,056** | 603ms/秒 |
| **10,000** | **10,000（全員1部屋）** | 999,900,000通/秒 | 1,528,832 | **998,371,168** | 602ms/秒 |

→ 組み立てだけでも**約150万通/秒が天井**。
   全員1部屋なら **300人までは捌けるが、1,000人で完全に破綻**する（必要量の15%しか処理できない）。
   1万人でも **15人ずつのルームに分ければ捌ける**（落ちるのは1.8%）。

→ **人数そのものより「1ルームの人数」で決まる**ことが、この数字でも裏づけられた。

## 測るときに踏んだ落とし穴

- **ルーム指定のフィールドは `rm`**（`room` ではない）。間違えると全員が1ルームへ入り、
  「ルームに分けても通数が減らない」という誤った結果になる
- ローカルはログイン無しだと**全員が管理者**になる。管理者の位置は
  **イベント全体（全ルーム）**へ配られるので、ルーム分割の意味が消える。
  テストでは `devRole: 'user'` を付けてお客さんとして入る（Render上では効かない）
