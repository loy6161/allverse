## イベント／ルーム・権限・チャット — 実装済み（2026-07-29確定）

### 場所の構造: イベント ＞ ルーム

- **イベント**が動画と再生位置の持ち主。同じイベントなら**全ルームが同じ動画・同じ再生位置**で同期する
- **ルーム**はイベント内の分割（定員30人）。呼び名は「ルーム」で統一
  - 理由: 北極星が「VRChatができない人のため」なので、VRC文化の語彙（インスタンス）を入口に置かない。
    VRC勢は「ルーム」→「インスタンスのことか」と翻訳できるが、逆は成立しないため。UIには「＝VRChatでいうインスタンス」と注記する
- 常設イベント `main`（表示名 VERSE CITY）は必ず存在し削除できない。いつ誰が来ても入れる場所を保証するため
- 特別イベントは管理者が画面から作成。**イベント定義はTursoに保存**（Render無料はスリープでメモリが消えるため）
- ルーム一覧から好きな部屋へ移動できる。入場時は「おまかせ」で自動割当も可

### イベントの所有者とVIPの運営権限（2026-08-02 変更・実装済み）

**きっかけ**: 「管理者（loyさん）がいない時も、ブラウザ会場だけを配信と連動して使うメンバーが出てくる。
それだとVIPのいまの権限だと運用むづかしいよね」。実際、旧VIPはイベントを立てられず動画も触れないため、
**管理者不在では会場を開くことすらできなかった**。

**採った形**: 役職は増やさず、**VIPを「出演者兼運営」にする**。ただし
**イベントに「立てた人」を記録し、自分が立てたイベントだけ操作できる**ようにした。
これが無いと、別のVIPが進行中のライブを閉じられてしまう。

| できること | ゲスト | 一般 | VIP | 管理者 |
|---|:---:|:---:|:---:|:---:|
| 全ルームに現れる | ✖ | ✖ | ✔ | ✔ |
| キック（時間指定つき） | ✖ | ✖ | ✔ | ✔ |
| **イベントを立てる** | ✖ | ✖ | **✔** | ✔ |
| **自分が立てたイベントの操作**（動画・設定・閉じる・合言葉の閲覧） | ✖ | ✖ | **✔** | ✔ |
| 他人が立てたイベントの操作 | ✖ | ✖ | **✖** | ✔ |
| BAN・BAN一覧・キックの履歴 | ✖ | ✖ | ✖ | ✔ |

- 判定は `canManageEvent(role, email, ev)`。合言葉の配り分けも**イベントごと**になった
  （VIPは自分のイベントの合言葉だけ見える）。クライアントには `mine` で伝える
- イベント作成はHTTP（入場画面）とWSの両方でVIPに開放。**イベント0件でも会場を開ける**
- ⚠ ログイン未設定（ローカル開発）では従来どおり全員が管理者相当

### キックのタイムアウト（2026-08-02 追加・実装済み）

旧キックは「蹴るだけで即戻れる」でBANとの間が空きすぎていた。loyさん設計:

> タイムアウト時間を設定して追えば、実質BANに近い扱いはできる。
> で、キックの履歴は管理人に通知して、あとでBANするか審議する。

- 選べる時間は **0 / 5 / 15 / 60 / 180分**（0＝従来どおり即戻れる）
- 相手の識別は**入場ログと同じ匿名ID**（`u:ハッシュ` / `g:番号`）。
  → **BANでは止められなかったゲストにも効く**
- 締め出しはイベント単位。**再起動しても解けない**（Tursoに保存し起動時に復元）
- **履歴は時間の有無にかかわらず残す**（タイムアウトが切れても消えない）。
  管理者の👥パネルに出し、同じ人が何回蹴られたかも数えて添える＝BAN審議の材料
- キックがあると**その場の管理者へ通知**が飛ぶ（VIPが蹴った場合も気づける）

⚠ **効き目には差がある。** ログイン済みの相手はアカウントのハッシュで追うので確実に効くが、
**ゲストはブラウザに保存した匿名IDが根拠**なので、保存を消せば別人として入り直せる。
本気の荒らしは止められない（＝ログイン必須にするかBANが要る）。
狙いは「その場を冷やす」ことで、完全な締め出しではない。

⚠ **機能追加より前からあるイベントは `ownerEmail` が空**なので、VIPは操作できない（管理者のみ）。
判定側で空文字同士が一致しないよう `Boolean(email)` で守っている。

### NPC（賑やかし）の人数（2026-08-02 変更）

「NPCが邪魔」という声があり、二段構えにした。

- **管理者はグローバル**: イベント設定の `npcMax` が全員に効く上限。-1 は自動（キャパ − 実在人数）
- **ユーザーはローカル**: 🚪パネルのスライダーで自分の画面だけ減らせる。設定は端末に保存
- **上限は超えられない**。だから**管理者が0にすれば全員の画面から消える**
- ⚠ 「グローバル」は「同じNPCが全員に見える」ではなく「**上限が共有される**」の意味。
  NPCは各自の画面だけの存在（サーバー同期は未確定リストの別項目）

### ゲストの見た目（2026-08-02 変更・実装済み）

**サーバーが匿名IDから決める。クライアントの申告は一切使わない。**

| 項目 | 値 |
|---|---|
| 髪型 | **なし**（ゲスト専用。選択肢に出さないのでログイン済みはこの姿になれない） |
| アクセ | なし |
| 服の形 | `middle` 固定 |
| **肌の色・服の色** | **匿名IDから決まる**（同じブラウザなら毎回同じ） |

計算は `src/guestlook.js`。**サーバーとクライアントが同じファイルを読む**（別々に持つと片方だけ直したときに姿がズレる）。
⚠ 引数は**接頭辞つきの完全な匿名ID**（`g:<番号>`）。落とすと別の色になる。

**なぜこうしたか**

- **髪なし**（loyさん決定）… 服の形は人が密集すると埋もれるが、髪型のシルエットは遠目で読める。
  「髪の毛なし」なら**新しい3Dアセットが要らない**（アクセの `none` と同じ仕組み）うえ、
  頭がまるごと肌色の面になるので**色による個体識別が一番強くなる**
- **色をばらけさせる**… 全員同じ姿だと荒らしがいても「どのゲストか」を指させない。
  キックは一覧から名前を選ぶので、**目の前の人とリストを結びつけられないと機能しない**
- **サーバーが決める**… 以前は「クライアントがランダムに決めた姿をサーバーが固定の姿に差し替える」形で、
  **本人の画面と他人の画面で姿が違っていた**（本人は気づけない）。
  確定した姿を `welcome` の `av` で本人にも返すようにして解消した

⚠ **7/14に入れたランダム初期値には理由が記録されていなかった**ため、
7/29の「ゲストは見た目を固定」と噛み合わないまま同居していた。同じ失敗を繰り返さないよう、
このように**なぜそうしたかを必ず残す**（WHY.md §31）。

### 会場チャットの記録（2026-08-02 追加・実装済み）

**「何かあった時に証拠になるので」**（loyさん）という理由で、会場での発言を開催に紐づけて残す。

| 記録する項目 | 補足 |
|---|---|
| どの開催か | `run_id`。**イベントを閉じても消さない** |
| 時刻・ルーム | |
| 発言者 | 表示名＋**匿名ID**（同名の人がいても取り違えないため） |
| 本文 | 最大200文字（既存のチャット上限） |
| 範囲 | `local`（会場内）/ `stream`（配信にも送信） |

- **見られるのは管理者だけ。** 📊イベントの記録から、直近20件を画面表示＋全件をCSV
- **ブロックで一部の人に見えなかった発言も残す。** ブロックは見え方の話で、
  「起きたこと」は起きたことなので、証拠としては残っている必要がある
- ゲストは発言できない仕様なので、**残るのはログイン済みの人の発言だけ**
- YouTubeチャット連動のイベントでは会場チャット自体を使わないため、記録も無い
- 記録の失敗で会話を止めない（ブロードキャストが先、保存は投げっぱなし）
- 容量: 1発言200文字上限。1配信で数百件でも数百KB程度で、Tursoの無料枠から見て誤差

### 入場前の断り書き（2026-08-02 文面変更）

**項目を並べる書き方をやめ、汎用的な書き方にした**（loyさん指示）。

> 入場すると、このブラウザに匿名の番号を保存し、イベントでの記録（入退場や発言など）が保存されます。
> 記録は主催者がイベントの運営・記録のために使います。メールアドレスそのものは保存しません。

**理由**: 記録するものが増えるたびに文面を直すのは続かないし、直し忘れると
「書いていないものを記録している」状態になる。何を記録するかを列挙するのではなく、
**「イベントでの記録が残る」ことを伝える形**にしてある。

### 権限（4段階）

| 権限 | 決まり方 | できること |
|---|---|---|
| admin | `ADMIN_EMAILS` に載っているGoogleアカウント | 動画の入力・再生操作・イベント作成/削除。全ルームに現れる |
| vip | `VIP_EMAILS` に載っているGoogleアカウント | 全ルームに現れる（姿・チャット・エモート）。動画は操作できない |
| user | Googleログイン済み | 通常の参加 |
| guest | 未ログイン | 入場と閲覧のみ。**チャット・エモート・見た目の変更は不可**。アバターはサーバーが固定 |

- 動画の**音量とミュートは各自ローカル**（共有しない）
- 「全ルームに現れる」= 姿・チャット・エモートが同一イベントの全ルームへ届く。本人に見えるのは自室のみ
- **移行の安全策**: `GOOGLE_CLIENT_ID` 未設定の間は全員が今まで通り使える（権限制御は設定した瞬間から効く）
- 権限の判断はサーバーが唯一の正（`welcome.canControl`）。クライアントで二重判定しない
- 設定手順は **SETUP_AUTH.md**

### 表示名と設定の引き継ぎ（2026-07-29確定）

- **表示名はサーバーが決める**。ログイン済み＝Googleアカウントの表示名、未ログイン＝`ゲスト001` の連番。
  クライアントからは名乗れない（`join.n` / `update.n` は無視）
  - 理由: Googleの表示名は**YouTubeのコメントに出る名前と同じ**でコミュニティ内では既に公開名であり、
    かつサーバーが決めることでなりすましを構造的に防げる
  - 名前は入場後も変更不可。変えられるのは見た目だけ
- **見た目は次回に引き継ぐ**。ブラウザ（localStorage）に保存し、ログイン済みならTursoの `profiles` にも保存して
  別の端末でも同じ姿で入れる。名前は保存しない（サーバーが決めるため）

### チャットのスコープ

- `local`（既定）… ワールド内だけに届く。YouTubeには流れない
- `stream` … 配信にも流す想定。**管理者のみ**送信でき、YouTube送信そのものは未実装
- 既定をlocalにした理由: **配信に出た発言は取り消せない**ので、不可逆な方をデフォルトにしない

### NPC（賑やかし・負荷テスト）

**自動補充が既定**（2026-07-30変更）。人が少ない時間帯でも会場が寂しく見えないよう、
**定員の空きぶんをNPCで埋める**（定員30・実在3人なら27体）。人が増えるとその分だけ減る。

- NPCは **自分の画面にだけ出る**。サーバーには送らないので、他の人の画面には出ない
- 実在の人と取り違えないための決まりごと:
  - 名前は **`NPC:なまえ`**、ネームプレートは灰色で一段地味にする
  - 発言は**頭上の吹き出しだけ**。チャット欄には流さない
    （チャット欄に出すと会話に見えて、返事をしても無視されることになるため）
  - 人数表示には数えない。`3 人（+NPC 27）` のように別枠で出す
- 管理者は 🚪 パネルから0〜100体で**人数を指定できる**（負荷テスト用）。
  指定すると自動補充は止まり、「自動」ボタンで戻せる
- 例外: `?npc=1` とオフラインデモモード（サーバー未接続）は自動補充を止めて固定7体
- 実測（2026-07-29）: **アバター1体につき描画コール約10・三角形約450**。
  100体で描画コール約1,100・三角形約5万。三角形は余裕だが**描画コールが先に効く**

### 迷惑行為への対処（2026-07-30追加）

| 手段 | 使える人 | できること |
|---|---|---|
| **ブロック** | 誰でも | その人と**お互いに**見えなくなる。姿・発言・エモートが双方向で消える |
| **キック** | 管理者・VIP | その場から退出させる。**すぐ入り直せる**（頭を冷やしてもらう用） |
| **BAN** | 管理者 | Googleアカウント単位で再入場を止める。理由を添えられる |

画面は右下の 👥 パネル。人の名前が並び、権限に応じてボタンが出る。

- **ブロックを相互不可視にした理由**: 片方向だと、ブロックした相手にこちらの発言が届き続ける。
  それでは嫌がらせへの対処にならない
- **ブロックを相手に知らせない理由**: 「ブロックされた」と分かると、別アカウントでの追跡や
  周囲を巻き込んだ揉め事につながる。静かに縁を切れる方が安全
- **管理者・VIPをキック/BANの対象にしない理由**: 蹴り合いになると収拾がつかない
- **ゲストをBANできない理由**: BANはGoogleアカウント単位。ゲストは次に来たら別人なので止められない。
  ゲストへの対処はキック、または**イベントを「ログインした人だけ」にする**
- ブロック一覧に**メールアドレスは出さない**。相手の連絡先を本人以外に見せないため、ハッシュで指す

### イベントの記録（2026-07-31追加・実装済み）

イベントを立ててから閉じるまでの動員を記録する。**閉じても記録は残る**（残らないなら記録の意味がない）。

**記録するもの**は「誰が・いつ入って・いつ出たか」の1行だけ（`visits` テーブル）。
1分ごとのサンプリング案は却下した。入退場の2点方式の方が **正確**（ピークを取りこぼさない）・
**軽い**（1時間で数十行）・**滞在時間がそのまま取れる**の3点で優る。
同接の経過も、この1本を時刻順になぞれば完全に復元できる。

| 出せるもの | 出し方 |
|---|---|
| 同接の経過 | 入退場を時刻順に増減してなぞる |
| ピーク同接・その時刻 | 上のなぞりの最大値（取りこぼしなし） |
| 累計ユニーク人数 | 訪問者IDの種類数 |
| のべ入場回数 | 行数 |
| 滞在時間（平均・中央値・最長） | 1行ごとの差 |
| 平均同接 | のべ滞在時間 ÷ 開催時間 |

**累計の数え方は「案A」（2026-07-31 loyさん決定）**

| 相手 | 数え方 | 保存されるもの |
|---|---|---|
| ログイン済み | Googleアカウント単位。別端末でも同じ人 | メールの**ハッシュ**（`u:`＋sha256の先頭16桁）。生のメールは残さない |
| ゲスト | ブラウザに保存した匿名の番号。同じブラウザなら同じ人 | ランダム16バイト（`g:`＋16進32桁）。名前もメールも紐づかない |

- 保存先は `localStorage['allverse.visitor.v1']`。消せば別の番号になる。追跡・広告には使わない
- **断り書きはルーム選択画面の「入場する」の真上**（`src/placepick.js` の `.vc-place-terms`・
  2026-07-31 loyさん指示）。入る前に読める場所に置くのが趣旨なので、会場が閉まっているときは出さない。
  **文面は事実だけを並べた暫定**で、最終的な言い回しはloyさんが決める
- NPCはサーバーに繋いでいないので最初から数に入らない（人数の水増しは起きない）

**単位は「開催（run）」**。`run_id = イベントid + 立てた時刻` で、イベントidが将来使い回されても
過去の開催と混ざらない。ルーム間の移動は1回の滞在として続ける（ルーム＝インスタンスなので来場は同じ1回）。
イベントをまたぐ移動だけが記録上の「退場→入場」になる。

**再起動への備え**: 人がいる間だけ1分ごとに「サーバーが生きている印」(`meta.heartbeat`)を書く。
次の起動時、退場が書かれないまま残った行をその時刻で閉じる（`closed_by='restart'`）。
今の時刻で閉じるとRenderのスリープ時間ぶん滞在が水増しされるため。**記録のズレは最大1分**。

**見せ方**: 🚪パネルの末尾に「📊 イベントの記録」（管理者だけ）。同接の折れ線、要約、CSV2種。
グラフの刻みは開催時間から自動で決める（1分固定だと短いイベントの山がまるごと消えるため）。
CSVはExcelの文字化けを避けるためBOM付きUTF-8。

**API**

| 口 | 用途 | 認証 |
|---|---|---|
| `POST /api/admin/logs` | 開催の一覧＋要約 | 管理者（IDトークン。URLに載せないためPOST） |
| `POST /api/admin/log` | 1開催の明細・経過・CSV（`format`）| 同上 |
| `GET /api/stats.json` | **PORTALが集計を取りに来る口** | `Authorization: Bearer <STATS_TOKEN>` |

PORTAL連携は**案1（こちらがAPIを出し、PORTAL側が取りに来る）**を採った。
本番DBの書き込み鍵をこちらに置かずに済むため（VRChat連携と同じ考え方）。
`STATS_TOKEN` 未設定ならこの口は開かない（無効が既定）。集計値だけを返し、訪問者ごとの行は出さない。
→ 申し送りは `HANDOFF_PORTAL.md`

## フェイズ2: チャットのYouTube一本化（2026-08-02 設計確定・実装未着手）

> **実装の着手OKはまだ出ていない。** ここは相談で確定した設計の記録。
> 発案と判断の経緯（loyさんの原文）は WHY.md §29。

### 基本方針

**YouTubeチャットを「発言の正本」にし、各空間はそれを再表現する場にする。**

```
YouTubeチャット   ＝ 公開される正式な発言ログ（正本）
ブラウザの吹き出し ＝ 空間内での発言表現（YouTube発言由来）
VRCの吹き出し     ＝ 別会場にいる本人の発言表現（同上）
```

- 動機: 配信中はYouTubeチャットが賑わうべきなのに、テストで**ブラウザ側チャットに書く人が多かった**。
  独自チャットを残すと会話がYouTubeとブラウザに分裂する
- **ブラウザ独自チャットは廃止方向**（YouTube連動イベントでは表示しない）。
  iframe埋め込みはYouTube本物のチャットUIなので、自由入力・スパチャ・メンバー表示・
  モデレーションが全部そのまま付いてくる＝独自実装は不要になる
- 副産物: **ゲスト入場の人もYouTube側にログインしていれば発言できる**
  （発言のハードルが会場のログインと切り離される）
- 運営向けの独自チャット監視画面も**不要**（YouTube Studioのモデレーションに乗る）

切り替えは**自動検知ではなく管理者の明示設定**（誤爆時に運営が制御を取り戻せるように）。

### YouTubeチャンネルの照合は「チャットに合言葉」方式（2026-08-02 確定）

**OAuth（`youtube.readonly`）は使わない。** 本人確認は、本人にしかできないことをやってもらう形にする。

1. ログイン済みの人が会場で「連携する」を押す → 短い合言葉が出る（例 `ALLVERSE連携:7K2A`）
2. **本人がYouTubeチャットにその合言葉を1回送る**
3. Worker（チャットを読んでいる）が該当発言を見つけ、その `authorChannelId` と
   ALLVERSEアカウントを結びつけて保存する
4. 以降ずっと有効。**連携は一生に1回**

**なぜこれで本人確認になるか**: あるチャンネルとして発言できるのはその持ち主だけなので、
**発言できたこと自体が証明**になる（SMS認証と同じ発想。向きが「受け取る／送る」で逆なだけ）。

**実装上の決めごと**
- 合言葉は**短時間で失効・1回限り**。**最初に送った人が勝ち**（本人が必ず先に送るので成立）
- 連携情報はTursoに保存（ALLVERSEアカウント ⇔ channelId）
- ⚠ **連携は任意のごほうび**。連携していない人のコメントも会場には流れる（下記2b/2cの切り分け）。
  連携すると「自分のアバターも喋る」だけ。押し付けにしない

**却下: チャンネルID/URLの自己申告だけで済ませる案**（2026-08-02）
チャンネルIDは公開情報なので誰でも他人のIDを入力できる。
**他人の発言を自分のアバターに喋らせられる／本人の連携を先取りで妨害できる**ため不可。
「持っていると言う」ことと「持っていると証明する」ことの差。

**保留: チャンネル概要欄に合言葉を貼る方式**（チャットに出したくない人向けの代替）
チャンネルの概要欄は公開情報なのでAPIキーだけで読め、編集できるのは持ち主だけなので
これも本人確認として成立する。ただし手間が多い（編集→確認→削除）と判断し、
**まずはチャット方式だけで出して反応を見る**（2026-08-02 loyさん判断）。
抵抗が大きければこちらを追加する。

### この方式で消えたもの（2026-08-02）

OAuthをやめたことで、以下は**すべて不要になった**。過去の検討記録として残す。

| 消えたもの | 内容 |
|---|---|
| Googleアプリ審査 | `youtube.readonly` はセンシティブスコープ。未審査だと**新規100人上限（生涯通算・リセット不可）**＋警告画面。有料のCASA審査（$15,000〜$75,000）はGmail/Drive/Fitnessのみで**YouTubeは対象外**だった |
| 今のログインの劣化 | 基本スコープだけの現ログインにセンシティブスコープを足すと、**ログイン全体が警告つき・100人上限**になっていた |
| プライバシーポリシー必須・公開ホームページ必須 | 審査要件だった |
| **入口の鍵との衝突** | 審査は「鍵の内側にないホームページ」を要求するため、`ENTRY_KEY` と両立しなかった |
| 独自ドメイン（有料の可能性） | `allverse.onrender.com` で審査を通せるか不明だった。**課金判断ごと消滅** |

⚠ **将来OAuthを使う判断をするときは、上の制約が全部復活する。** 特に「今のログインを壊す」点に注意。

### 書き込み（投稿）の扱い（2026-08-02 確認）

| やり方 | 判定 | 理由 |
|---|---|---|
| **iframe埋め込みからの投稿** | **問題なし** | 投稿先はYouTubeのページそのもの。こちらのAPIを1回も使わない |
| こちらのUIから代理投稿 | **不可** | ①各ユーザーの書き込み権限（OAuth）が要る＝100人上限が再来 ②**書き込みは1回50単位・1日10,000単位＝200発言で枯渇**（実績は1配信800〜1,000件） |
| 運営からのクロスポスト | 条件付き可 | 許可を出すのは運営1人なので上限は無関係。ただし**1日200件の枠**は残る＝枠の拡大申請が前提 |

### 実装の段階（2a → 2b → 2c）

| 段階 | 内容 | 依存 |
|---|---|---|
| 2a | イベント設定にチャット連動フラグ／連動時は独自チャット非表示／**運営メッセージ固定枠**（INFO/IMPORTANT/EMERGENCY・Turso永続化） | なし |
| 2b | PC: `https://www.youtube.com/live_chat?v=<動画ID>&embed_domain=<ドメイン>` をiframe埋め込み／スマホ: 開くボタン。**あわせてYouTubeのコメントを会場に流す**（連携不要・全員に効く） | ⚠ iframe内ログイン投稿が3rd-party Cookie制限で失敗しうる（**本番ドメインで要実測**）。スマホでのlive_chat URL直開きも実測 |
| 2c | 合言葉でchannelIdを照合 → ブラウザ＋VRCの**本人アバター**に吹き出し | **Unity側Workerとの協議（HANDOFF必須）**。Google審査は不要になった |

### 2cの取り決め事項（Unity側と協議して決める）

- YouTubeチャット取得は**Worker一本化の合意どおりWorker側**（こちらで二重実装しない）
- **合言葉の照合もWorker側**でしかできない（チャットを読んでいるのがWorkerのため）。
  Worker → ALLVERSE への「連携できました」の通知経路が新たに要る
- 照合キー（channelId）を公開の presence.json に生で載せない。
  **ハッシュ化して載せる／Worker専用の認証付き口を作る**のどちらかにする（プライバシー）
- presence v=1 は凍結のまま。吹き出しは既存の `web[].c` の枠（実装済み・既定OFF）を
  使うか、live.json 側に持つかをWorkerの構造を見て決める
- 表示制御（40〜60文字・数秒・距離制御・NGフィルタ）はWorker通過後の各空間側で行う
