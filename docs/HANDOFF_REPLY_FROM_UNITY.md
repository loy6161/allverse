## 2. 統合方針（こう決めた）

### 2-1. VRCワールドは presence.json を直接読まない（理由：5秒制限の取り合い）

VRChatの文字列ダウンロードは**クライアントあたり5秒に1回**しかできない。
ワールドは既に ALLVERSE Worker の `/v1/live.json` をその枠で取得予定のため、
presence.json を別枠で張ると両方とも約11秒間隔に劣化し、「5秒で歩行補間」の想定が崩れる。

そこで：

```
ブラウザ版サーバー ──GET /api/presence.json──▶ ALLVERSE Worker（サーバー間・4秒キャッシュ）
                                                     │ live.json に "web":[…] として同梱
                                                     ▼
                                              VRCワールド（従来どおり約5秒ポーリング1本）
```

- **そちらの改修はゼロ**。presence.json は公開GETのままでよい
- ts鮮度判定（60秒で退場処理）はWorker側で行い、ワールドには空配列を渡す
- Render無料プランのスリープ復帰遅延もWorker側で吸収する（直近キャッシュを返す）
- **お願い**: Render公開時にURLをこのフォルダのmdか loyさん経由で共有してほしい（Workerの環境変数に設定する）

### 2-2. マスター取得＋同期変数は採用しない（VRC側裁量の範囲）

PRESENCE_SPEC §2.4 の推奨と異なり、**全クライアントが各自Workerを取得する方式**にする。
理由：ALLVERSE側ギミック全体が「同期変数ゼロ」設計で統一されており、群衆表示では
クライアント間の数秒の位置差は実害がないため。歩行補間（約5秒かけて移動）は推奨どおり実装する。

### 2-3. YouTube取得の一本化は「逆向き」を提案（§6 案Aの修正案）

PRESENCE_SPEC §6 は「ブラウザ側サーバーに一本化（VRCは yt[] を読む）」を推奨しているが、
ALLVERSE Worker が既にYouTube取得の本実装を持つ予定（応援スコア集計・スパチャ・NGフィルタ・
アイコン承認配信・リアクション取得まで担当）。二重開発を避けるため：

- **YouTube系のデータはALLVERSE Workerを正とする**。presence.json の `yt[]` は実装不要（空のままでよい）
- ブラウザ版ワールド内にYouTubeチャットを表示したくなったら、逆に**Workerのエンドポイントを提供する**ので連絡してほしい
- 「ワールド内チャット→YouTubeクロスポスト」（そちらで優先決定済み）はポータルのGoogle認証と絡むため、
  ALLVERSE Phase 1（ポータル設計）に合流させて一緒に設計したい

### 2-4. ログ中間ソフトは1本に統合する

PRESENCE_SPEC §3.2 の「中間ソフト」は、ALLVERSE側で設計済みの **harvester**
（loyさんPC常駐・output_log監視・コイン台帳 `[ALLVERSE]` 行をWorkerへPOST）と同一物。
別々に作らず、**1本のharvesterが `[VCITY1]` 行はそちらの `/api/vrc-presence` へ、
`[ALLVERSE]` 行はWorkerへ送り分ける**形で実装する（Phase 3で実装予定）。
`[VCITY1]` のUdonロガー（毎秒・スタッフスイッチ・既定OFF）は依頼どおり仕込む。
スタッフ用Bearerトークンの発行方法が決まったら共有してほしい。
